## Ruby 3.3.12 attempt: dead end while on Rails 4.2

- Heroku's currently-supported Ruby versions are `3.3.12`, `3.4.10`, `4.0.6` (per https://devcenter.heroku.com/articles/ruby-support). Ruby `3.1.6` (this branch's target) is already EOL per Heroku's own policy, deployable "at your own risk" only.
- Installed Ruby `3.3.12` locally (`brew upgrade ruby-build` was needed first; the old ruby-build didn't know about it) and pointed the Gemfile at it.
- A genuinely fresh `bundle install` for Rails `4.2.11.3` cannot succeed on Ruby 3.2+, under any Bundler version:
  - Rails 4.2.11.3's own gemspec declares `bundler >= 1.3.0, < 2.0`. Bundler 2.5.22 (default with Ruby 3.3.12) refuses to resolve the Gemfile because of it.
  - Bundler 1.17.3 (the last 1.x release) itself crashes immediately on Ruby 3.2+ (`NoMethodError: undefined method 'untaint'` — the taint mechanism was fully removed in Ruby 3.2, only deprecated-but-present in 3.1).
  - So: Bundler 2.x can't resolve the Gemfile; Bundler 1.x can't run. No version satisfies both sides.
- The Bundler error message names the actual fix: the `bundler < 2.0` constraint applies to `rails >= 4.0.0.beta1, < 5.0.5.rc1`. **Rails 5.0.5+ is where it was lifted.** Reaching any Heroku-supported Ruby version requires bumping Rails to at least ~5.0.5 first — this is not optional, and not just a "Heroku policy" issue, it's a real dependency-resolution wall.
- Correction to an earlier claim in this session: "Bundler 2 works fine with Rails 4.2" was based on running `bundle check`/`bundle exec` against an *already-resolved* lockfile, which doesn't re-invoke the dependency solver. That masked the real constraint; it only surfaces on a genuine fresh install.
- Reverted local state back to Ruby `3.1.6` (`.ruby-version`, Gemfile `ruby` line) after this probe. `Gemfile.lock` was never touched by the failed 3.3.12 attempt (resolution failed before any lockfile write), so no revert was needed there.
- Conclusion: Ruby `3.1.x` is the real technical ceiling for Rails 4.2, not just a "good enough for now" choice. Getting to a genuinely Heroku-supported Ruby means Rails must move first.

## Security audit (manual + Brakeman)

- Ran `brakeman` (installed standalone via `gem install brakeman`, since the full `development` group bundle install hit an unrelated dead gem, `meta_request 0.3.4`, pulled from RubyGems by its author). Brakeman doesn't need the app's bundle to run a static scan.
- **Critical, actively fixed this session**: `config/initializers/secret_token.rb` had a hardcoded `secret_key_base` committed in plaintext, unconditionally applied via `Transbucket::Application.config.secret_key_base = '...'`. Verified in Rails 4.2.11.3's actual source (`railties/lib/rails/application.rb`) that `secrets.secret_key_base ||= config.secret_key_base` — i.e. `secrets.yml`'s value wins if present, this hardcoded one is only a *fallback*. Since `SECRET_KEY_BASE` was never set as an env var on either `transbucket` or `transbucket-staging` (confirmed via the original config-key audit above), `secrets.yml`'s `ENV["SECRET_KEY_BASE"]` evaluated to nil on both apps, so **the exposed hardcoded value was very likely the actual live secret_key_base on production**, meaning anyone with repo access could forge session cookies for any user, including admins.
  - No way to determine after the fact whether this was ever exploited: no audit-trail gem (`paper_trail`/`audited`/etc.) exists in the app; `lograge` is enabled in production but has no `custom_options` configured, so even surviving request logs wouldn't show *who* made a request; Papertrail is on the free `choklad` plan on both apps, with short retention, and this file looks old enough (Rails 4.0-era scaffolding) to predate any surviving logs regardless.
  - Remediated: rotated `SECRET_KEY_BASE` as a Heroku config var (fresh `SecureRandom.hex(64)`, generated per-app, values never displayed) on both `transbucket` (now serving `v389`) and `transbucket-staging` (`v320`) — this needed no code deploy/build, since config var changes just restart the dyno on the existing release, so it wasn't blocked by heroku-20's build restriction. ## Production DNS outage: transbucket.com hard down, fixed live

- Diagnosed and fixed a live production outage, unrelated to any code in this repo. `transbucket.com` (bare apex, not `www`) was completely unreachable over HTTPS; `www.transbucket.com` and `transbucket.herokuapp.com` both worked fine (`200 OK`), proving the app/dyno/database were healthy the whole time.
- Root cause: Gandi's "Web Forwarding" feature (a legacy redirect service, separate from real DNS records) was installing a plain `A` record pointing the apex at a Gandi IP that only answers HTTP (301 to `http://www.transbucket.com`), not HTTPS at all — confirmed directly (`curl` succeeded on port 80, failed to connect at all on 443). Heroku's own requirement for this domain (`heroku domains --app transbucket`) is an `ALIAS`/`ANAME` record to `spherical-dogwood-....herokudns.com`; a real `CNAME` isn't legal at a zone apex per the DNS spec, which is why `www` (a real CNAME) worked and the apex didn't.
- Likely origin: this domain was still on Gandi's legacy DNS platform (not LiveDNS), which doesn't support `ALIAS` records at all — Web Forwarding was probably the only apex-pointing option available when this was first set up, long before HTTPS-everywhere made that gap fatal.
- Confirmed the fix wouldn't break Heroku's SSL: the ACM cert for `transbucket.com` had `status: succeeded` with `updated_at: 2026-07-16` (i.e. it renewed successfully within the last ~7 weeks, meaning DNS must have validated correctly at that time) and is currently valid/trusted through Oct 13 — so pointing DNS back at Heroku wouldn't require issuing a new cert.
- Verified no DNSSEC was in play before approving Gandi's "this will break DNSSEC" warning on adding the ALIAS record (`dig ... DS`/`DNSKEY` both empty — no chain of trust exists for this domain, so nothing to break).
- User made the actual changes in Gandi's dashboard (removed Web Forwarding, migrated to LiveDNS, added the `ALIAS` record — first attempt used name `transbucket.com` instead of literal `@`, which Gandi's API rejected with a clear error; second attempt correct). Verified from this session at each step via `dig`/`curl` against multiple resolvers (system, Google `8.8.8.8`, Cloudflare `1.1.1.1`) and a `curl --resolve` forcing a direct connection to Heroku's IP, confirming the whole chain (DNS → TLS cert → app) works end-to-end.
- Remaining, harmless side effect: `transbucket.com` now serves the app directly rather than redirecting to `www` (no code-level host-canonicalization exists — checked `application_controller.rb`/`production.rb`, only `config.force_ssl = true`). Not fixed as part of the outage response; a follow-up if canonical-www behavior matters later.
- No code, Heroku config, or database was touched to fix this — pure DNS, at Gandi, entirely outside this repo's or Heroku's control.

## Security fixes: round 4 (live IDOR via PinForm's user_id + pin_params permit!)

- Investigated the last item from the earlier Brakeman audit (`params.require(:pin).permit!` in `pins_controller.rb`) and found something worse than the original "no whitelist" framing: `PinForm` declared `property :user_id` as an ordinary writable property with **no protection at all**. Empirically proved (a real `PinForm.new(attacker.pins.new)`, `.validate` with a crafted `user_id`, then `.save` + reload) that any authenticated user could create or update a pin attributed to an **arbitrary other user** — persisted, not just theoretical.
