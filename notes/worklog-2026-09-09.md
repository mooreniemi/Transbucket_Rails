## Sticky footer and comment timestamp fixes (local, not yet deployed)

- Root-caused a footer layout report ("footer floating outside the page, not locked to the bottom") on `/pins/141` and confirmed via direct DOM inspection that it reproduced identically regardless of locale, ruling out the locale work as the cause.
- Found and fixed a long-standing (2014-era, present on `master`) unclosed `<div class="row">` in `app/views/pins/show.html.erb`. Browsers silently auto-corrected this by consuming the layout's `.container` closing tag to close the stray `.row` instead, leaving `.container` itself unclosed so the footer and the dev-only `any_login` widget rendered nested inside it rather than as true siblings. Invisible under the old CSS; it broke the new flexbox sticky-footer rule below because that depends on `.footer` genuinely being a body-level sibling.
- Added an actual flexbox sticky-footer implementation to `app/assets/stylesheets/styles.css.scss` (`html{height:100%}`, `body{display:flex;flex-direction:column;min-height:100%}`, `.container{flex:1 0 auto}`, `.footer{flex-shrink:0}`), and removed `body`'s now-obsolete `padding-bottom: 70px` (previously invisible trailing whitespace; became a visible gap under the footer once it was the true last flex item).
- Verified locally (Selenium, `.footer`'s parent chain and bounding rect) on `/pins/141` in `en` and `zh-CN`, plus sanity-checked `/pins`, `/procedures`, `/surgeons`, and `/newsfeed` for regressions. Footer now sits flush with the viewport bottom on short pages and inline after content on long pages.
- Local dev environment setup needed for this: `thin ~> 1.8` fails to boot under this Ruby/Rack combo (`wrong number of arguments` in `rack/handler/thin.rb`) — used `rails server webrick` instead. Local Postgres runs via `docker-compose.override.yml` on host port 5433, not the default 5432. A 22-hour-old stale Spring preloader was masking template edits behind cached fragments/compiled views; `bundle exec spring stop` plus `DISABLE_SPRING=1` resolved it. Local DB was empty (`User.count == 0`); ran `rake db:seed` (genders/procedures/surgeons already existed from a prior partial run, so only `test_users.rb` and `some_pins.rb` needed to run) to get a real `meowmeow` login and seeded pins for testing. Local seed login is `meowmeow` / `big fake password for testing`, not `password` as used against staging.
- Separately audited whether displayed dates/times are localized: found exactly one date rendered anywhere in the app (`comments/_comment.html.erb`), hardcoded as raw `strftime('%b %d, %Y at %I:%M %p')`, bypassing I18n entirely (zero uses of `l()`/`I18n.l` existed anywhere in the codebase). The `catalog.yml` consolidation already carries full `date`/`time`/`datetime` format data for all 15 locales; confirmed via direct `I18n.l` calls that it produces correct locale-appropriate output (verified en/de/es/fr/ja/zh-CN/ru/ar).
- Also confirmed storage is correctly UTC (`Time.zone` is UTC, `ActiveRecord::Base.default_timezone == :utc`) but display had no timezone conversion at all — every visitor saw the same raw UTC instant with no indication it wasn't their own local time.
- Fixed both together: `_comment.html.erb` now renders `<time datetime="<UTC ISO8601>" class="local-time"><%= l(comment.updated_at, format: :long) %></time>` (locale-correct, UTC-instant fallback for no-JS), and a new `app/assets/javascripts/local_time.js` progressively enhances every `.local-time` element via `Intl.DateTimeFormat(...)` on `ready`/`page:load`, which converts the UTC instant to the viewer's actual local clock using their browser's own timezone. Verified end-to-end locally: server-rendered German fallback read `Donnerstag, 10. September 2026, 02:44 Uhr` (correct format, still UTC wall-clock); after JS ran, the same element read `September 9, 2026 at 10:44 PM` (correctly shifted to the test browser's local timezone).
- First pass used `navigator.language` (the browser's own language setting) as the `Intl.DateTimeFormat` locale, which caused the timestamp to silently flip to English on a `pt-BR` page whenever the test browser's language was English, while every other string on the page stayed Portuguese -- caught by spot-checking the rendered page, not by the earlier automated check. Fixed by using the page's own `<html lang>` locale instead (`document.documentElement.lang`, already rendered by the layout), so the timestamp's language matches the rest of the page regardless of the visitor's browser language; local-timezone conversion is unaffected since that's controlled by the separate, omitted `timeZone` option. Re-verified across `pt-BR`/`de`/`ja`/`en`: each stays in its own page language while still showing the correct local-shifted time (`9 de setembro de 2026 às 22:44` / `9. September 2026 um 22:44` / `2026年9月9日 22:44` / `September 9, 2026 at 10:44 PM`).
- None of this session's fixes have been deployed to staging or production yet.
